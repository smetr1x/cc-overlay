# Запросы для показателей оверлея

Имена метрик — ожидаемые, фактические фиксируются в фазе 1 ([telemetry-verification.md](telemetry-verification.md), строка 10). Запросы выполняет overlay-api; подстановки в фигурных скобках делает он же.

Обозначения:

- `T` — `claude_code_token_usage_tokens_total`
- `C` — `claude_code_cost_usage_USD_total`
- `A` — `claude_code_active_time_total_seconds_total`
- `{X}` — `session_id` текущей сессии
- `{W}` — длина окна, например `5h` или `43200s`
- `{L}` — глубина поиска значения до начала окна, `7d`

## Модель данных

Claude Code шлёт cumulative-счётчики ([ADR-0001](adr/0001-temporality.md)). Каждая комбинация `session_id`, `type`, `model`, `query_source` и прочих атрибутов — отдельная серия, которая начинается с нуля и растёт, пока жив процесс. Отсюда два следствия:

1. Текущее значение серии уже равно итогу с начала сессии.
2. Сумма по сериям сессии равна итогу сессии, какие бы новые атрибуты ни появились.

## Почему не `increase()` и не `rate()`

`increase()` считает разность между первой и последней точкой окна и экстраполирует её на границы окна. Для наших серий это даёт две ошибки.

**Теряется первое значение серии.** Серия появляется в Prometheus уже с ненулевым значением: первый экспорт несёт токены первого ответа API. Предыдущей точки с нулём нет, поэтому `increase()` это значение не учитывает. Потеря повторяется для каждой сессии и каждой новой пары модель/тип внутри сессии. Первый ответ обычно содержит крупный `cacheCreation`, так что недосчёт заметный.

**Экстраполяция.** Если серия покрывает окно не целиком, `increase()` домножает результат. Для счётчика токенов получаются дробные и завышенные числа.

`rate()` — это `increase()`, делённый на длину окна, с теми же ошибками.

Плюс `increase()` один: он корректно переживает сбросы счётчика. В нашей модели сбросов быть не должно, а если они случаются, их ловит страж (см. ниже).

## Шаблон «итог за окно»

```promql
sum(
    last_over_time(M[{W}])
  - (
      last_over_time(M[{L}] offset {W})
      or
      last_over_time(M[{W}]) * 0
    )
)
```

Как читать, для каждой серии отдельно:

- `last_over_time(M[{W}])` — значение в конце окна. Серии без точек в окне сюда не попадают, и это правильно: прироста у них не было.
- `last_over_time(M[{L}] offset {W})` — последнее значение до начала окна.
- `or last_over_time(M[{W}]) * 0` — для серии, родившейся внутри окна, значения «до» нет, подставляется ноль. Тогда серия вносит всё своё значение целиком.

Зачем `{L}` вместо простого `M offset {W}`: мгновенный селектор видит точку не старше 5 минут. Если серия перед началом окна молчала дольше, она выглядела бы как новая и внесла бы всё значение вместо разности — итог задвоился бы. `last_over_time` с глубиной 7 дней находит значение «до» независимо от пауз.

Дальше этот шаблон записывается как `Δ{W}(M)`. Селектор может содержать фильтры, например `Δ5m(T{session_id="{X}"})`.

Шаблон точен при одном условии: внутри окна счётчик не сбрасывался.

## Страж корректности

```promql
sum(resets(T[{W}])) > 0
```

`resets()` считает, сколько раз значение серии уменьшалось. Если результат непустой, overlay-api выставляет показателям этого окна флаг `approximate`, а оверлей помечает их знаком `~`. Возможные причины сброса: возобновление сессии под прежним `session_id` или запасной путь через `deltatocumulative`.

## MVP: показатели из метрик

### Текущая сессия

Что считать текущей сессией, определяет overlay-api: это живая сессия (последняя точка моложе двух интервалов экспорта) с самым поздним изменением счётчика. Момент изменения API отслеживает сам при опросе, а после рестарта восстанавливает через `query_range` за последние 12 часов. Это логика с unit-тестами, выражать её в PromQL нецелесообразно. Если живых сессий несколько, оверлей показывает значок «+N».

Список живых сессий:

```promql
time() - max by (session_id) (timestamp(T)) < 10
```

Токены по типам:

```promql
sum by (type) (last_over_time(T{session_id="{X}"}[{L}]))
```

Стоимость, подпись `≈$`:

```promql
sum(last_over_time(C{session_id="{X}"}[{L}]))
```

`last_over_time`, а не мгновенное значение, чтобы показатель не исчезал, если последний scrape был пропущен.

Модель — та, на которую пришлось больше всего токенов основного диалога за 5 минут; вспомогательные запросы к младшей модели не должны её подменять:

```promql
topk(1, sum by (model) (Δ5m(T{session_id="{X}", query_source="main"})))
```

При пустом результате (сессия молчит) берётся модель с наибольшим итогом: `topk(1, sum by (model) (last_over_time(T{session_id="{X}", query_source="main"}[{L}])))`.

Длительность показывается двумя числами. Активное время — документированная метрика, сумма по `type="user"` и `type="cli"`:

```promql
sum(last_over_time(A{session_id="{X}"}[{L}]))
```

Время от начала сессии:

```promql
time() - min(min_over_time(timestamp(T{session_id="{X}"})[12h:15s]))
```

Подзапрос дорогой, но момент начала сессии не меняется: API вычисляет его один раз на сессию и кэширует.

### Скорость за последние 5 минут

По всем сессиям, потому что расход подписки общий.

```promql
Δ5m(T{type!="cacheRead"}) / 5     # токенов в минуту
Δ5m(C) * 12                       # ≈$ в час
```

Используется тот же шаблон, а не `rate()`: один проверенный тестами путь вместо двух и никакой экстраполяции. Недостаток — показатель реагирует ступенькой, а не плавно; для окна в 5 минут это приемлемо.

### Cache hit ratio текущей сессии

```promql
  sum(last_over_time(T{session_id="{X}", type="cacheRead"}[{L}]))
/
  sum(last_over_time(T{session_id="{X}", type=~"input|cacheRead|cacheCreation"}[{L}]))
```

Формула из ТЗ: доля входных токенов, прочитанных из кэша. Если знаменатель пуст или равен нулю, результат пустой или `NaN` — API отдаёт `null`, оверлей показывает «нет данных».

### Сегодня

`{W}` — число секунд с локальной полуночи в часовом поясе из `TZ`; его вычисляет API, потому что в PromQL длина окна должна быть константой.

```promql
Δ{W}(T{type!="cacheRead"})        # токены без чтения кэша
Δ{W}(T{type="cacheRead"})         # чтение кэша, отдельной строкой
Δ{W}(C)                           # ≈$
```

Чтение кэша показывается отдельно: по объёму оно обычно на порядок больше остального и скрыло бы реальную динамику.

### Скользящее окно 5 часов

```promql
Δ5h(T{type!="cacheRead"})
Δ5h(C)
```

Подпись: «ориентир, не официальный лимит». Настоящий процент лимита приходит из status line ([ADR-0009](adr/0009-statusline-bridge.md)); когда он есть, этот показатель уходит на второй план.

### Свежесть данных

```promql
time() - max(timestamp(T))
```

Работает только при `send_timestamps: true` в экспортёре коллектора: иначе `timestamp()` возвращает время scrape, а не время точки. Значение больше 10 секунд (два интервала экспорта) при живой сессии означает статус `stale`.

Здоровье конвейера проверяется отдельно: `up{job="otel-collector"}` и `up{job="overlay-api"}`.

## Фаза 4: показатели из событий

Loki принимает OTLP нативно. Resource-атрибут `service.name` становится меткой `service_name`, атрибуты события попадают в structured metadata, точки в именах заменяются подчёркиваниями: `event.name` → `event_name`, `session.id` → `session_id`. Имена полей проверяются в фазе 4 на реальных данных.

`session_id` и `prompt_id` остаются в structured metadata и не становятся метками: у меток с высокой кардинальностью Loki резко теряет производительность.

Последний запрос к API (вызов `query_range`, `limit=1`, `direction=backward`):

```logql
{service_name=~"claude-code.*"} | event_name="api_request"
```

Поля `model`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens`, `duration_ms`, `cost_usd` читаются из structured metadata найденной записи.

Число ошибок за 5 минут:

```logql
sum(count_over_time({service_name=~"claude-code.*"} | event_name="api_error" [5m]))
```

Последняя ошибка — тот же приём с `limit=1`; показываются `status_code`, `model`, `attempt`. Текст ошибки на экран не выводится.

Латентность, 95-й перцентиль за 5 минут:

```logql
quantile_over_time(0.95,
  {service_name=~"claude-code.*"} | event_name="api_request" | unwrap duration_ms [5m]
) by ()
```

### Заполнение контекста

Основной источник — `context_window.used_percentage` из status line. Оценка по событиям нужна как запасной вариант и для истории в Grafana.

Берётся последний запрос основного диалога текущей сессии:

```logql
{service_name=~"claude-code.*"} | event_name="api_request" | query_source="main" | session_id="{X}"
```

Оценка: `input_tokens + cache_read_tokens + cache_creation_tokens`. Документация status line считает `used_percentage` по той же формуле, без выходных токенов. Если после этого запроса пришло событие `compaction` с `success="true"`, берётся его `post_tokens`.

Ограничения, которые делают число приближением:

- размер окна контекста в телеметрии не передаётся, он задаётся в конфиге overlay-api по имени модели;
- выходные токены последнего ответа войдут в контекст следующего запроса, но в оценку не входят;
- между запросами оценка не обновляется.

## Тесты на синтетике

Генератор `tools/synth` шлёт OTLP с известными числами, тест сравнивает ответ `/api/v1/snapshot` с ожидаемым. Обязательные сценарии:

1. Две параллельные сессии — итоги не смешиваются и не теряются.
2. Серия рождается внутри окна с ненулевым первым значением — оно учтено целиком.
3. Сессия молчит дольше 5 минут, затем продолжает, и граница окна попадает на паузу — итог не задвоен.
4. Сессия началась до полуночи и продолжается после — в «сегодня» попадает только прирост после полуночи.
5. Счётчик сбрасывается — выставлен флаг `approximate`.
6. Процесс завершён — статус `idle`, а не `stale`, и нигде нет нулей вместо `null`.
7. Тот же набор в режиме delta + `deltatocumulative` — проверка запасного пути.
