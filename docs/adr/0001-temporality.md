# ADR-0001. Cumulative temporality у источника вместо `deltatocumulative`

Статус: принято (2026-11-16). Отклонение от ТЗ, п. 2 «Известные грабли», п. 1–2.

## Контекст

Claude Code по умолчанию экспортирует метрики с delta temporality: каждая точка несёт прирост за интервал. Prometheus хранит cumulative-счётчики. ТЗ предлагает ставить в коллекторе процессор `deltatocumulative` с `max_stale: 1h`.

При сверке с документацией выяснилось, что Claude Code поддерживает `OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE=cumulative`.

## Решение

В блок `env` файла `~/.claude/settings.json` добавляется `OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE=cumulative`. Процессор `deltatocumulative` в конвейер не включается.

## Альтернативы

**Delta + `deltatocumulative` (вариант ТЗ).** Отклонён как основной по трём причинам:

- Процессор в статусе alpha и хранит накопленные суммы в памяти. Рестарт коллектора обнуляет счётчики всех идущих сессий, и «итог за сессию» становится неверным без какого-либо сигнала.
- Серия, молчавшая дольше `max_stale`, удаляется и при следующей точке начинается с нуля. Значение `1h` из ТЗ не покрывает обеденный перерыв; большое значение превращает процессор в утечку памяти.
- При delta молчащая сессия не шлёт ничего. Состояние «данные устарели» из ТЗ («нет обновлений дольше двух интервалов экспорта») срабатывало бы при каждой паузе пользователя.

**Delta ingestion в Prometheus.** Экспериментальная возможность, не проверялась; для учебного проекта лишний риск.

## Почему так

Принцип: состояние держит тот, кому оно принадлежит. Счётчик сессии принадлежит процессу Claude Code; он знает точное значение и может сообщать его целиком. Пересчёт прироста обратно в сумму в промежуточном звене создаёт второе место хранения состояния, которое может разойтись с первым.

Cumulative у источника также снимает грабли №2 из ТЗ (out-of-order между параллельными сессиями): каждая сессия — отдельный процесс со своим `session.id`, потоки не пересекаются.

## Последствия

- Конвейер коллектора становится stateless: его рестарт безопасен.
- Появляется различимое состояние `idle` против `stale` ([architecture.md](../architecture.md)).
- `OTEL_METRICS_INCLUDE_SESSION_ID` остаётся `true`. Отключение сломало бы и этот вариант тоже.
- Объём данных немного растёт: неизменившиеся серии экспортируются каждый интервал. Для десятков серий это несущественно.
- Генератор `tools/synth` поддерживает оба режима, а e2e-тесты прогоняются и для delta + `deltatocumulative`. Запасной путь остаётся проверенным на случай, если cumulative в beta-телеметрии поведёт себя иначе.

## Дополнение по итогам фазы 1

Запасной путь реализован вторым приёмником в том же коллекторе: порт 4319, конвейер `metrics/delta` с процессором `delta_to_cumulative` (новое имя `deltatocumulative`). Порт наружу не публикуется. Основной конвейер на 4317 процессора не содержит.

Так запасной путь проверяется тем же `make test-e2e`, что и основной, и переход на него сводится к публикации порта и смене адреса в настройках Claude Code.

На синтетике (Go SDK) подтверждено: cumulative-итоги точны, молчащая сессия переэкспортирует точки.

На настоящем Claude Code 2.1.319 пункты 1 и 2 ниже подтверждены 2026-11-17: за 112 секунд молчания возраст последней точки остался меньше секунды. Решение остаётся в силе. Пункт 3 открыт и на решение не влияет.

## Что проверить на настоящей сессии

1. Claude Code действительно шлёт cumulative-точки с этой переменной.
2. Неизменившиеся серии переэкспортируются каждый интервал. Если нет, определение `stale` пересматривается.
3. Поведение при `--resume`: сохраняется ли `session.id` и с какого значения стартует счётчик.

Если пункт 1 не подтвердится, решение меняется на вариант ТЗ отдельным ADR.
