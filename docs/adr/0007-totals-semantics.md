# ADR-0007. Итоги считаются разностью значений, а не `increase()`

Статус: принято (2026-11-16). Отвечает на п. 3 «Известных граблей» ТЗ.

## Контекст

Оверлей показывает итоги за сессию, за сегодня и за скользящие окна. Серии Claude Code короткоживущие: рождаются с сессией, с каждой новой моделью и типом токенов, и умирают с процессом. ТЗ требует обосновать выбор между `increase`, `max_over_time`, `last_over_time` и покрыть его тестами.

## Решение

- Итог за сессию: `sum(last_over_time(M{session_id="X"}[7d]))`.
- Итог за окно: разность значения в конце окна и последнего значения до его начала, с нулём для серий, родившихся в окне. Полная формула и разбор — в [queries.md](../queries.md).
- Скорость считается тем же шаблоном за 5 минут, без `rate()`.
- Страж `sum(resets(M[W])) > 0` выставляет показателю флаг `approximate`.

## Альтернативы

**`increase()`.** Не учитывает первое значение серии и экстраполирует границы окна. Для серий, которые рождаются уже с ненулевым счётчиком, это систематический недосчёт. Единственное преимущество — устойчивость к сбросам.

**`max_over_time()`.** Для монотонного счётчика совпадает с `last_over_time`. При сбросе возвращает наибольший из отрезков вместо их суммы, то есть скрывает проблему, не решая её.

**Расчёт в overlay-api по сырым точкам.** API мог бы запрашивать точки и суммировать положительные приросты сам. Это точно при любых сбросах, но тогда Grafana считала бы иначе, чем оверлей.

**Recording rules.** Заранее вычисленные серии ускорили бы запросы. При десятках серий ускорять нечего; вернуться к этому стоит, если запросы за 30 дней в Grafana станут медленными.

## Почему так

Принцип: формула должна опираться на инвариант, который обеспечен архитектурой и проверяется в работе. Инвариант — «счётчик внутри сессии не сбрасывается». Его обеспечивает [ADR-0001](0001-temporality.md), а `resets()` проверяет при каждом запросе. Пока инвариант выполняется, разность значений точна до токена.

Выбор «точная формула плюс страж» вместо «устойчивая, но всегда неточная» сделан потому, что недосчёт `increase()` постоянный и незаметный, а сброс счётчика редкий и теперь заметный.

## Последствия

- Запросы длиннее и требуют пояснения; оно дано в `queries.md`.
- Шаблон один на все окна, поэтому тестируется один раз: семь сценариев на синтетике перечислены в `queries.md`.
- Grafana использует те же выражения с `$__range` вместо вычисленного окна.
- Глубина поиска значения «до» равна 7 дням. Сессия, молчавшая дольше и затем продолжившаяся под тем же `session.id`, даст завышение; случай считается нереалистичным.
- В Prometheus 3 появились экспериментальные модификаторы селекторов диапазона, которые могут упростить формулу. В фазе 0 они не проверялись; решение от них не зависит.
