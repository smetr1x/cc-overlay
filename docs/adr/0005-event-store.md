# ADR-0005. События в Loki через нативный OTLP

Статус: принято (2026-11-16). Подтверждает решение по умолчанию из ТЗ. Реализация — фаза 4.

## Контекст

События Claude Code (`api_request`, `api_error`, `compaction` и другие) приходят сигналом logs. Они нужны для блока «последний запрос», для латентности и для оценки заполнения контекста. Бюджет памяти стека ограничен.

## Решение

Loki в режиме одного бинарника с хранением на локальной файловой системе. Коллектор отправляет логи экспортёром `otlphttp` на `http://loki:3100/otlp`. Хранение — 30 дней, как у метрик.

Метка индекса одна — `service_name`. Все атрибуты событий, включая `session_id`, `prompt_id` и `event_name`, остаются в structured metadata.

Loki и Grafana вынесены в compose-профиль `history` и включаются по требованию. *(Изменено в фазе 4: Loki в ядре, см. дополнение.)*

## Альтернативы

**Файл или SQLite внутри overlay-api.** Меньше памяти, но пришлось бы самим писать приём OTLP, схему, очистку по сроку и запросы, а Grafana осталась бы без событий. Это повторение готового инструмента.

**Без событий вообще.** Оверлей MVP действительно обходится метриками. Отклонено, потому что латентность запросов и ошибки API есть только в событиях.

**Экспортёр `loki` из contrib.** Документация Loki предписывает `otlphttp`; старый экспортёр упаковывал атрибуты в JSON и требовал ручной разметки меток.

**VictoriaLogs.** Легче по памяти. Не выбран: Loki ближе к связке, которая встречается в работе, и использует Grafana как штатный интерфейс.

## Почему так

Принцип: каждому сигналу — хранилище его типа. Метрики отвечают на вопрос «сколько», события — «что именно произошло»; попытка хранить события в Prometheus привела бы к взрыву кардинальности по `prompt_id`.

Structured metadata вместо меток: метка с уникальным значением на каждую сессию создаёт в Loki отдельный поток на сессию, и запросы за неделю начинают перебирать тысячи мелких потоков.

## Дополнение по итогам фазы 4 (2026-11-17)

**Loki перенесён из профиля `history` в ядро стека.** Из него overlay-api берёт последний запрос, ошибки API и латентность, и эти строки нужны в оверлее постоянно, а не только когда открыта Grafana. Измеренная память — 50–107 МБ, лимит контейнера 192 МБ. Grafana осталась в профиле `history`.

Ядро вместе с Loki: коллектор 50 МБ, Prometheus 50 МБ, Loki до 107 МБ, overlay-api 8 МБ — около 215 МБ, в бюджет ТЗ в 500 МБ укладывается. С Grafana (190–275 МБ) — около 490 МБ, на границе.

Что подтверждено сквозным тестом на синтетике:

- коллектор отправляет события экспортёром `otlp_http` (новое имя `otlphttp`) на `/otlp`;
- метка потока одна — `service_name`; атрибуты событий лежат в structured metadata с `_` вместо точек: `event_name`, `session_id`, `query_source`, `duration_ms`, `status_code` и т. д.;
- `unwrap duration_ms` работает по structured metadata;
- идентификаторы пользователя и `tool_parameters` до Loki не доходят.

Текст ошибки (`error` в `api_error`) в Loki сохраняется — он нужен для разбора в Grafana, — но в оверлей не передаётся.

Если Loki остановлен, коллектор держит события в очереди на 500 пачек и через 2 минуты повторов отбрасывает. Метрики и метрика заполнения контекста от этого не зависят: коннектор стоит в том же конвейере, но не за экспортёром Loki.

## Последствия

- С профилем `history` стек выходит на границу бюджета в 500 МБ (замеры — в дополнении выше и в [architecture.md](../architecture.md)).
- overlay-api работает без Loki: блок `events` получает `available: false`, окно показывает «Loki недоступен», остальное не страдает.
- Имена полей после преобразования (`event.name` → `event_name`) подтверждены на синтетике; на настоящих событиях Claude Code имена атрибутов те же (проверено отладочным выводом коллектора в фазе 2).
- В конвейере логов те же правила удаления идентификаторов, что и в конвейере метрик ([ADR-0008](0008-privacy.md)).
