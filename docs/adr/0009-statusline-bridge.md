# ADR-0009. Мост из status line: реальный процент лимита и заполнение контекста

Статус: принято (2026-11-16). Отклонение от ТЗ: п. 1 «Не цели» (процент лимита Pro) и перенос части фазы 5 в фазы 2–3.

## Контекст

ТЗ исключает показатель «процент израсходованного лимита Pro», потому что Claude Code не передаёт лимиты через OTel. Это верно. Вместо него ТЗ предлагает скользящее окно 5 часов с подписью «ориентир, не официальный лимит», а заполнение контекста — приближением по событиям.

При сверке обнаружено, что скрипт status line получает на stdin JSON, в котором есть:

- `rate_limits.five_hour.used_percentage`, `rate_limits.seven_day.used_percentage` и `resets_at` для обоих окон;
- `context_window.used_percentage` и `context_window.context_window_size`;
- `session_id`, `model`, `cost.total_cost_usd`.

Поле `rate_limits` есть только у подписчиков Pro, Max и Ultra и появляется после первого ответа API в сессии.

## Решение

В репозитории появляется скрипт status line. Он читает JSON, печатает короткую строку для терминала и отправляет выбранные поля в overlay-api: `POST http://127.0.0.1:8787/api/v1/statusline`. overlay-api хранит последнее значение по каждой сессии в памяти и включает его в снимок.

Оверлей показывает:

- процент 5-часового и 7-дневного лимита и время до сброса — как основные показатели;
- заполнение контекста из `context_window.used_percentage` — как основное;
- расчётное окно 5 часов по метрикам остаётся с прежней подписью и служит запасным показателем.

Скрипт передаёт только числа и идентификатор сессии. Пути, имена репозиториев и прочие поля JSON не отправляются.

## Альтернативы

**Оставить как в ТЗ.** Пользователь видел бы оценку в долларах API, которая не переводится в процент лимита подписки, хотя точное число доступно.

**Отложить до фазы 5.** Тогда в фазе 4 пришлось бы строить приближение заполнения контекста, которое после фазы 5 стало бы ненужным.

**Скрипт пишет в файл, overlay-api его читает.** Требует общего тома между WSL и контейнером и опроса файла. HTTP на localhost проще.

**Только status line, без OTel.** Для текущей сессии этого хватило бы: стоимость, контекст и лимиты там уже есть. Но нет истории, разбивки по типам токенов и моделям, событий и Grafana. Стек OTel оправдан историей и учебной целью проекта; это осознанный выбор.

## Почему так

Принцип: измеренное значение лучше вычисленного. Процент лимита считает сервер, которому известны правила подписки; любая оценка на нашей стороне эти правила угадывает.

Запрет ТЗ «не выдумывать показатель» при этом соблюдён: показатель берётся из документированного поля.

## Последствия

- Нужна правка `~/.claude/settings.json` (ключ `statusLine`). Она выполняется только с явного согласия владельца: агент показывает diff и не применяет его сам. На момент фазы 0 ключ `statusLine` в файле не задан, конфликта нет.
- Status line обновляется по событиям сессии, а не по таймеру. В простое значение стареет, поэтому снимок передаёт его возраст, и оверлей гасит показатель старше настраиваемого порога. Параметр `refreshInterval` позволяет обновлять принудительно.
- Отправка не должна тормозить терминал: таймаут запроса 200 мс, ошибки игнорируются. При недоступном overlay-api строка в терминале всё равно печатается.
- Новая точка входа с записью в overlay-api. Она слушает только `127.0.0.1`, проверяет схему и ограничивает размер тела.
- Значения status line хранятся только в памяти. Чтобы они попали в историю, overlay-api публикует их как собственные gauge-метрики, и Prometheus собирает их вместе с остальными.
- Формат JSON status line сверен с документацией в начале фазы 2: поля `rate_limits.*`, `context_window.used_percentage`, `context_window.context_window_size`, `session_id`, `model.display_name` на месте.

## Реализация (фаза 2)

- Скрипт — `statusline/cc-overlay-statusline.sh`, нужны `jq` и `curl`. Фильтр `jq` пропускает наружу только перечисленные поля; контракт приёма — в [api.md](../api.md).
- Таймаут отправки 0,3 с вместо задуманных 0,2: меньше ложных срывов при первом запросе после простоя.
- Точка приёма отклоняет запросы с заголовком `Origin` и с типом содержимого, отличным от `application/json`: так страница в браузере не может подделать отчёт.
- Предполагается, что `session_id` в status line совпадает с `session.id` в телеметрии. На лимиты это не влияет (они общие для аккаунта), на контекст влияет; проверяется на настоящей сессии.
